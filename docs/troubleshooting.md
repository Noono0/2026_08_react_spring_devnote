## 1. 매물 금액이 잘못 저장됨

- **현상**: 크롤러가 수집한 CSV에서 제목이 `2억 2,400만원`인 매물의 `보증금(만원)` 칸이 `22400`이 아니라 `20002`였습니다.
- **원인**: 금액 파서가 `억` 뒤의 쉼표에서 숫자 읽기를 멈춰 `2,400`을 `2`로 읽었습니다. 층수도 `총 4층 중 3층`처럼 전체 층수가 앞에 오는 표기에서 전체 층수를 고르는 문제가 함께 있었습니다.
- **해결**: 쉼표가 들어간 `억`·`만` 금액을 끝까지 읽도록 고치고, `해당층/전체층`·`5층중4층`·`반지층` 같은 표기를 구분했습니다. 제목과 본문의 층수가 서로 다르면 자동으로 단정하지 않고 원문을 남깁니다.
- **결과**: 실제 CSV에 나온 표기를 그대로 `CrawlerListingParserTest`에 회귀 테스트로 넣었습니다(현재 15개 사례). 같은 표기가 다시 깨지면 빌드에서 바로 실패합니다.

## 2. 1MB가 넘는 파일만 업로드 실패

- **현상**: 로컬 개발 서버에서는 20MB 이미지도 올라가는데, Docker·운영 환경에서는 1MB가 넘는 첨부·이미지가 `413`으로 실패했습니다.
- **원인**: 백엔드(Spring)는 파일 20MB·요청 25MB까지 허용하지만, 앞단 Nginx의 기본 `client_max_body_size`가 1MB라 요청이 백엔드에 닿기 전에 거절됐습니다. Vite 개발 서버에는 이런 제한이 없어 로컬에서는 드러나지 않았습니다.
- **해결**: `frontend/nginx.conf`에 `client_max_body_size 25m`를 넣어 Spring의 요청 한도와 맞췄습니다.
- **배운 점**: 요청이 지나가는 계층(브라우저 → Nginx → Spring → 디스크)마다 크기 제한이 있습니다. 한 곳만 바꾸지 말고 가장 앞단부터 같은 값으로 맞춰야 합니다.

## 3. 첫 화면 JS 1,078kB

- **현상**: 포트폴리오 홈만 열어도 메인 JS가 1,078.93kB(gzip 333.57kB)였습니다.
- **원인**: 모든 페이지와 Tiptap 리치 텍스트 편집기를 첫 화면 번들에 함께 넣고 있었습니다. 방문자 대부분은 편집기를 열지 않습니다.
- **해결**: 홈 외 페이지를 `React.lazy`로 나누고, 공통 `PageOutlet`의 `Suspense`에서 로딩 상태를 처리했습니다. 포트폴리오 편집기는 실제로 열 때만 내려받습니다. 이후 페이지 파일을 못 받는 경우(재배포 직후 열려 있던 탭)를 위해 `PageErrorBoundary`로 안내 화면도 추가했습니다.
- **결과**: 메인 JS 약 472kB(gzip 약 148.5kB)로 **약 56% 감소**했습니다. 나머지 코드는 필요할 때 별도 파일로 내려받습니다.

## 4. 안 쓰는 업로드 파일 정리의 함정

- **현상**: 편집 중 올렸다가 지운 이미지가 `TEMP` 상태로 서버 디스크에 계속 쌓였습니다.
- **처음 생각한 해결**: "하루 지난 `TEMP` 파일을 지운다" — 그대로 적용했다면 **이미 저장한 글의 본문 이미지가 깨졌을 것**입니다.
- **원인**: 문서를 저장할 때 대표 이미지·첨부만 `ACTIVE`로 바꾸고, 본문에 넣은 이미지는 `TEMP`로 남아 본문 HTML의 주소(`/api/v1/files/{id}/content`)로만 쓰이고 있었습니다. 상태값만으로는 쓰는 파일인지 판단할 수 없었습니다.
- **해결**: 문서·문서 이력의 썸네일과 본문 HTML, 첨부, 포트폴리오 썸네일·이미지 **어디에서도 쓰이지 않는** `TEMP` 파일만 고르도록 SQL을 작성했습니다. 삭제 직전에 같은 조건을 다시 확인해, 조회 직후 쓰이기 시작한 파일은 남깁니다. `/files/1/`처럼 끝에 `/`를 붙여 1번 파일이 12번 주소에 잘못 일치하지 않게 했습니다.
- **결과**: 실제 MySQL(Testcontainers)에서 7가지 경우(본문·이력 본문·첨부·포트폴리오에서 사용, 최근 업로드, 사용 중 파일, 미사용 파일)를 확인하는 테스트를 추가했습니다.

## 5. 테스트가 인자 없이 mock을 호출함

- **현상**: 새로 쓴 테스트가 `Cannot destructure property 'cursor' of 'undefined'`로 실패했습니다. 화면 코드는 항상 객체를 넘기고 있었습니다.
- **원인**: `beforeEach(() => mockedApi.mockReset())`처럼 중괄호 없는 화살표 함수는 `mockReset()`의 반환값(mock 함수 자신)을 돌려줍니다. Vitest는 `beforeEach`가 함수를 돌려주면 "테스트 뒤 정리 함수"로 보고 **인자 없이 호출**합니다.
- **해결**: `beforeEach(() => { mockedApi.mockReset(); })`처럼 중괄호로 감싸 아무것도 돌려주지 않게 했습니다.
- **배운 점**: 화살표 함수의 "암묵적 반환"은 반환값이 의미를 갖는 API(정리 함수·Promise)와 만나면 의도치 않은 동작을 만듭니다.

## 6. 새 DB에서만 글 저장이 500 오류

- **현상**: 기능 확인용으로 빈 MySQL을 새로 띄우자 업무 History 글 저장이 500 오류로 실패했습니다. 로그에는 `Field 'use_yn' doesn't have a default value`가 남았습니다. 테스트(Testcontainers)와 운영 서버에서는 같은 코드가 정상 동작했습니다.
- **원인**: `schema.sql`은 `use_yn CHAR(1) NOT NULL DEFAULT 'Y'`로 테이블을 만들지만, 로컬 기본 설정(`JPA_DDL_AUTO=update`)에서는 Hibernate가 기동할 때마다 `alter table documents modify column use_yn char(1) not null`을 실행했습니다. Entity의 `columnDefinition = "char(1)"`에 기본값이 없어서 그 정의대로 컬럼을 다시 만들면서 `DEFAULT 'Y'`를 지운 것입니다. 문서 INSERT는 `use_yn`을 넣지 않고 기본값에 맡기고 있었습니다. 테스트와 운영은 `validate`라 이 ALTER가 실행되지 않아 드러나지 않았습니다.
- **해결**: `documents`·`members`·`portfolio_sections`의 `use_yn`·`current_yn` Entity 정의에 `schema.sql`과 같은 기본값(`'Y'`·`'N'`)을 넣었습니다. 이미 기본값이 지워진 로컬 DB도 다음 기동 때 Hibernate가 기본값을 다시 붙입니다.
- **결과**: `update` 모드로 기동해 컬럼 기본값과 문서 저장을 확인하는 `LocalSchemaUpdateIntegrationTest`를 추가했습니다. 수정 전 코드로 돌리면 두 테스트 모두 실패하는 것을 확인했습니다.
- **배운 점**: 테스트·운영과 로컬의 스키마 관리 방식(`validate` vs `update`)이 다르면, 로컬에서만 생기는 문제는 테스트로 잡히지 않습니다. 같은 설정으로 기동하는 테스트를 하나 두면 이런 차이를 막을 수 있습니다.
